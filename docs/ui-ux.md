# video-vault UI/UX仕様 v1(2026-08-16)

自分専用の動画ダウンロードアプリ。**単一の入力欄がすべての入口**という設計。

商用アプリ `apps/personal-ai` の取込UX(`../../personal-ai/docs/capture-ux.md`)と同じ思想で、
**video-vaultが先行してその設計を実地で検証する実験場**になる。ここで確かめた挙動を商用版へ持っていく。

## 設計の決定(2026-08-16)

**デザインツール(Figma・Canva)は使わない。Composeでコードを書きながらUIを確定させる。**

理由:

1. **Figma→コードの経路はReact/Web向け**に作られており、Compose(Androidネイティブ)は対象外。
   Figma Make や Dev Mode 経由の変換が高い再現度を出すという報告はいずれもWeb系スタックの話で、
   Composeでは結局手で翻訳することになる。Figmaに投じた時間がコードにならない
2. **このアプリのユーザーは1人**。デザインシステムは他人に渡すための資産であり、渡す相手がいない
3. **最も検証すべきUXがFigmaではテストできない**——日本語IME(Input Method Editor、日本語入力)の挙動。
   競合Recallは入力欄で未確定文字列が勝手に確定する不具合を抱えていた(2026-08-15実測)。
   Figmaのプロトタイプに文字を打っても、Composeの `TextField` が日本語をどう扱うかは分からない。
   **検証対象がツールの外にある以上、そのツールで作ったプロトタイプは意思決定に使えない**

デザインの規範は **Material 3 Expressive**(Googleの現行デザインシステム)に全面的に乗る。
色・タイポグラフィ・余白・モーションを自分で設計しない。反復はAndroid Studioの
Compose Preview と Live Edit で実機に対して行う。

Canvaはアプリ内UIには使わない(アイコン・ストア素材・紹介ページ用のツール)。
video-vaultはストア配信しないため当面出番はない。

## スコープ境界

対象は「**ログインは必要だが、DRMで保護されていない**」動画まで。

- **ログイン必須 ≠ DRM保護**。会員制サイトの動画はCookieを渡せば取得でき、私的複製の範囲に収まる
- **DRM(Digital Rights Management、デジタル著作権管理。Widevine等)で暗号化された動画は対象外**。
  技術的に困難であることに加え、日本の著作権法では**技術的保護手段の回避を伴う複製が
  私的使用のための複製の例外から外れる**。私的利用かどうかとは別の論点になる
- この線引きを先に決めておかないと「あのサイトが取れない」という話が繰り返し出てくる。
  DRM判定に該当したら**エラーではなく「対象外」として明示的に弾く**設計にする

取得物はすべて私的利用限定。第三者への共有は行わない(モノレポCLAUDE.mdの規約どおり)。

## 単一入力欄(オムニボックス)

画面上で最も大きく、最も目立つ常設要素。**FABは置かない**(入力欄と役割が二重になる)。

### 入力に応じた判定と提示

判定は**端末内で即座に**行い、入力するそばから候補が並び替わる。
ユーザーが「これはURLだからこのボタン」と考える必要をなくす。

| 入力内容 | 判定方法 | 第一候補 | 第二候補 |
|---|---|---|---|
| 空 | — | クリップボードにURLがあれば「このリンクを開く」チップを1枚 | — |
| 動画サイトのURL | URLパターン表で照合 | **ダウンロード** | ブラウザで開く |
| その他のURL | スキーム(http/https)とドメイン形式 | **ブラウザで開く** | — |
| キーワード(日本語・英語) | URLとして解釈できない | **Googleで検索**(結果は内蔵ブラウザで開く) | — |

- URLパターン表は将来サイトが増えるため**コードに直接書かず、設定として分離**する
  (商用版ではサーバー配信にするが、video-vaultはアプリ内のJSONで足りる)
- 判定に迷ったら**両方の候補を出す**。ユーザーに選ばせるのは「意図が本当に曖昧なとき」だけにする
- クリップボードは `getPrimaryClipDescription()` のみを先読みし、
  `getPrimaryClip()` は**チップをタップした後**に呼ぶ(Android 12以降の貼り付けトーストを出さないため)

### 共有シートからの受け取り

YouTubeアプリやXアプリの共有メニューからも投げ込めるようにする(実装済みのintent-filterを活用)。
共有された場合は入力欄に貼られた状態でアプリが開き、判定済みの候補が既に並んでいる状態にする。

## ダウンロードの2導線

### 導線1: 公開リンク(ログイン不要)

入力欄にURLを貼る → 「ダウンロード」を選ぶ → yt-dlp が直接取得。

### 導線2: ログインが必要なサイト

1. 入力欄にサイトのURLを入れて「ブラウザで開く」
2. **内蔵ブラウザ(WebView)でユーザーが普通にログインする**
3. 目的の動画ページを開いた状態で、画面下部の**ダウンロードボタン**を押す
4. アプリが **WebViewの保持するCookieを取り出し**、現在のページURLと一緒に yt-dlp へ渡す
5. yt-dlp がCookieを使って取得する

**動画の通信を横取りして解析する方式は採らない。** サイト側の実装が変わるたびに壊れるため。
Cookieを渡す方式なら、サイト対応の追随は yt-dlp 本体に任せられ、こちらのコードはCookieを渡すだけで済む。

## 画面一覧

| 画面 | 役割 |
|---|---|
| **ホーム** | 単一入力欄 + クリップボードチップ + ダウンロード済み一覧(新しい順) |
| **内蔵ブラウザ** | WebView。下部にダウンロードボタンと進捗表示。戻る/進む/再読込 |
| **ダウンロード詳細** | 進捗、完了後は再生・共有(端末内)・削除。失敗時はエラー原文と再試行 |
| **設定** | 保存先、同時実行数、yt-dlp本体の更新、対象外サイトの一覧 |

画面数を増やさない。タブもドロワーも置かず、**ホームから2階層以内**に全機能を収める。

## 実装で最初に確かめること

**日本語入力の挙動**。ホームの入力欄に「かれの」と打ち、
未確定文字列が勝手に確定しないこと、変換候補が正しく出ることを実機で確認する。

これは商用版 personal-ai の差別化の中核(日本語ネイティブ)を支える技術的前提であり、
**ここが破綻するならUIの技術選定そのものを見直す**必要がある。Compose の `TextField` で
問題が出る場合は `BasicTextField` や独自の入力接続を検討する。
