## 現在地: 画面を閉じてもダウンロードが続くようになった(2026-08-25)

**ForegroundService化**(`data/DownloadService.kt` + `data/DownloadCenter.kt`)と、
**内蔵ブラウザでダウンロードを始めてもホームへ戻さない**変更を実装した。
人間の「ダウンロードしながら動画の再生を継続できるか」という問いが出発点で、
それまでは(a)バッジを押すとホームへ飛んでWebViewごと破棄され再生が止まる (b)画面を離れると
ダウンロードごと死ぬ、の2つが重なって不可能だった。両方を潰してある。

**エミュレータ上で煙試験20シナリオ・72チェックすべて合格**(`scripts/smoke-test.sh`)。単体テスト30件合格。

- 構造の要点は `../CLAUDE.md`「ダウンロードの実行」が正。**実行状態と履歴の持ち主を
  ViewModelから `DownloadCenter`(プロセス寿命のobject)へ移した**のが中核
- **画面が無い間に終わった結果は `DownloadCenter` が抱えて、次に画面が付いたとき1度だけ渡す**。
  これが無いと、アプリを閉じている間に終わったダウンロードの結果が(通知を切っている人には)
  どこにも出ない。煙試験のシナリオ19で顕在化して足した
- 実機(Pixel)へはコミット `4ca5064` 相当のdebugビルドを2026-08-21に配布済み(**最新ではない**。
  次のアクション1で配り直す)
- 人の目での確認(通知の見え方・アイコン・日本語IME・操作感)はこれから(次のアクション1・2)

## 次のアクション(優先順)

### 1. 実機へ最新ビルドを配る(ポート番号をもらうところから)

実機は `adb devices` に `adb-56251FDCQ001BB-...` として**接続済みのことがある**(2026-08-21はmDNS経由で見えていた)。
見えていなければ、人間に Pixel の 設定 > システム > 開発者向けオプション > ワイヤレスデバッグ の
ポート番号を聞いて `adb connect 100.91.182.103:<ポート>`(別LANは先にMTUクランプ。`docs/dev-setup.md`)→ `scripts/deploy-device.sh`。

**実機で人に見てもらう点**(エミュレータでは確認できない):
- **動画を再生したままバッジでダウンロードを始め、再生が止まらないこと**(今回の変更の目的)
- **通知の許可ダイアログ**が初回起動で出ること、許可後に進捗通知と完了通知が出ること。
  通知の小アイコン(`ic_download`)が潰れて見えないなら専用の白抜きアイコンを起こす
- **アプリをタスクから消してもダウンロードが続くこと**(通知の「中断」で止められること)
- ランチャーの**アイコンと「ゲットVIDEO」の表示**。テーマアイコン(Android 13+の単色)も
- ダーク/ライトの両方での配色
- ブックマークタイルの**長押し削除**が指で自然か
- 履歴のシートの操作感

### 2. 【人間の操作が要る】日本語IMEの検証

入力欄に **「かれの」** と打ち、**未確定文字列が勝手に確定しないこと**・変換候補が正しく出ることを実機で見る。
今回のUI刷新で入力欄は `OutlinedTextField` → `TextField`(ピル型)に変えたが、
**値の同期更新という構造は変えていない**。それでも実機で確かめること。

- **なぜエージェントにできないか**: `adb shell input text` はIMEを経由せず直接文字を挿入するため、
  未確定状態そのものが再現しない。エミュレータの英語キーボードでも同様
- **なぜ重要か**: 商用版 `apps/personal-ai` の差別化の中核(日本語ネイティブ)を支える技術的前提。
  破綻するならUIの技術選定(Compose `TextField`)から見直す

### 3. 共有シートの実機確認

YouTubeアプリ → 共有 → ゲットVIDEO → 候補が並んだ状態で開くか。エミュレータにはYouTubeアプリが無く確認できない。

### 4. NewsPicks・TikTokの実地検証

**NewsPicksのGoogleログイン → 白画面は解決済み**(2026-08-21)。http(s)以外のスキームを
WebView内で止める実装で、ログイン後もアプリ内に留まりログインできることを実機で確認。

**NewsPicksの動画ダウンロードで `[Errno 7] No address associated with hostname` が出た**(実機)。
抽出は通るのに動画本体(CloudFront `vod.newspicks.com`)のセグメント取得だけがDNSで落ちる。
デュアルスタック回線での `getaddrinfo` のAAAA詰まり → **`--force-ipv4` を常時付与して対処**
(CLAUDE.md「yt-dlp運用の要点」4層目)。IPv4のみのエミュレータでは再現しないため、**実機で通るか要確認**。

**Xのパスキー2要素認証は通せない(Androidの制限。ui-ux.md「パスキー」)。**
ユーザーはXにパスキーのみ設定・パスワード削除済み。回避はX側で「認証アプリ(TOTP)」か「SMS」の
2要素認証を追加してもらうこと(依頼済み)。アプリは WebAuthn 呼び出しを検知して帯で案内する。

**Xログインの白画面・Googleログインが戻る・パスワード欄が出ない → すべて真因は同じ**:
WebViewの高さが WRAP_CONTENT で CSS の `vh`/`height:100%` が0に潰れていた(DevToolsで実測)。
`WebView.layoutParams = MATCH_PARENT` で解消。エミュレータでXログイン画面が全部描画されること、
`100vh` が 0→747 になることを確認済み。別ウィンドウ対応(`onCreateWindow`)と `adjustResize` も入れてある。
**実機でGoogleログインが完了するところまでは要確認**(エミュレータにGoogleアカウントが無く最後まで通せない)。

**TikTokのPlayストア誘導**: `play.google.com` 等のアプリストアへの遷移と、`intent://` の退避URLが
ストアの場合も止めるようにした(以前は退避URLを `loadUrl` で開いてしまい遮断をすり抜けていた)。
エミュレータでは tiktok.com のフィードが開き `<video>` にバッジが出る。実機で再度要確認。
それでもTikTok側が動画ページへの遷移を毎回アプリへ振るなら、⋮「PC版サイトで表示」を使うか、
TikTokアプリの共有からURLをこのアプリへ送る運用(判定表にあるので直接DLが走る)。

**内蔵ブラウザの調査は Logcat の `VideoVaultBrowser`**(`adb logcat -s VideoVaultBrowser:V`)と
**`scripts/webview-eval.py`**(ページ内でJSを評価)。uiautomatorはWebView内部のテキストを拾えないので、
中の状態はDevTools(CDP)で見る(debugビルドで有効)。

### 4b. 動画バッジ(2026-08-21・人間の依頼で導入)

ブラウザ内で `<video>`/埋め込みiframeを検出し、その枠の右下に弾む紫のバッジを重ねる
(`assets/video_badge.js`)。タップ→`VideoVault.onVideoDownload`→yt-dlp。常設フッターは廃止、
予備は下部バー「⋮」の「このページのURLでダウンロード」。
エミュレータのYouTube視聴ページで**注入→右下に表示→タップ→`Download/videos` に保存**まで確認済み
(煙試験シナリオ18)。**実機でNewsPicks・X・TikTokのページにバッジが出るかは未確認**。
出ないサイトがあれば `scripts/webview-eval.py <serial> <url> "document.querySelectorAll('video,iframe').length"`
で、動画がDOMに無い(canvas/Shadow DOM/クロスオリジンiframe)のか、注入が失敗しているのかを切り分ける。
- TikTokは判定表(`site_patterns.json`)に `downloadable: true` で載っているので、動画URLを貼れば直接走る
- NewsPicksは判定表に無い(yt-dlpに専用extractorが無い)。内蔵ブラウザでログイン→「このページをダウンロード」の
  Cookie導線で試す。通らなければ `downloadable: false` で登録して「対象外」と明示する

### 5. 会員制サイト(GFS)のDRM有無調査

**アプリを触る前にPC側のyt-dlpで検証する**。DRM(Widevine)なら対象外として
`app/src/main/assets/site_patterns.json` に `downloadable: false` で登録して終わり。

## 作業の始め方

```bash
cd ~/workspace/sc-products/apps/video-vault

# エミュレータ(自動テスト用。起動していなければ)
adb devices | grep emulator || \
  sg kvm -c "$ANDROID_HOME/emulator/emulator @medium_phone -no-window -no-audio -no-boot-anim -no-snapshot -gpu swiftshader_indirect" &

# 変更したら必ず: 実機へ配る前にエミュレータで通す
./scripts/smoke-test.sh                  # 全17シナリオ(数分かかる)
./scripts/smoke-test.sh --skip-download  # ネットワークを使わない範囲だけ(速い)

# 実機へ
adb connect 100.91.182.103:<ポート> && ./scripts/deploy-device.sh
```

- **非対話シェルでは `~/.bashrc` が読まれない**。`JAVA_HOME` と `ANDROID_HOME` を明示的に渡すか、
  スクリプト経由で実行する(スクリプトは自分で設定している)
- 煙試験を長時間の前景で待たない。バックグラウンドで走らせてログを監視する。**`cd` を忘れて空振りしやすい**
- 煙試験は冒頭で `pm clear` して履歴・ブックマークを初期化する。**エミュレータ上のデータは試験のたびに消える**

## つまずきどころ(すべて実際に踏んだ)

詳細は `docs/dev-setup.md`「踏みやすい落とし穴」と `CLAUDE.md`「yt-dlp運用の要点」。要点だけ:

1. **YouTubeのDLが403で落ちたら、原因は3層のどれか**。エラー文に `JavaScript runtime` が
   含まれるかで切り分ける。`--js-runtimes` を自分で渡してはいけない(ライブラリの自動付与を壊す)
2. **煙試験の合格判定を緩めない**。`.ytdl`(69バイトのレジューム情報)を成果物と誤認して
   偽の合格を出したことがある
3. **`tap_text` は完全一致を優先する**。ホームに「最近のダウンロード」見出しができたため、
   部分一致だけだと「ダウンロード」ボタンの代わりに見出しを押す
4. **実機のペアリングコードはダイアログを閉じると即失効**する。コードをもらったら即座に叩く
5. **別LANからのadbはMTUで固まる**。宛先限定のMTUクランプ(`sudo ip route replace 100.91.182.103/32 dev eth0 mtu 1000`)を、WSLを再起動するたびに張る
6. **エミュレータのウィンドウ表示は実用外**。人間の動作確認は実機で行うと決めてある
7. **`material-icons-core` にあるアイコンは限られる**(Add/Close/Delete/Refresh/Search/ArrowBack等)。
   それ以外は `res/drawable/ic_*.xml` に自作してある。`material-icons-extended` は入れない(APK肥大)
8. **永続化(JSONファイル)は単一スレッドで直列に書く**。保存のたびに `launch(Dispatchers.IO)` していたら
   同じ一時ファイルを取り合って古い状態が残り得る、起動時の非同期ロードが操作後の状態を上書きし得る、
   とCodexに指摘された(2026-08-21)。起動時ロードは同期、保存は `persist` dispatcher経由にしてある
9. **煙試験はビルド失敗で即終了する**。以前は `| tail -2` で終了コードが消え、古いAPKで合格し得た。
   ボタンを文言で特定するので、**同じ画面に同じ文言のボタンを2つ置かない**(ダイアログの確定は「保存」「削除」「消去」)
   **呼び出す側も同じ罠を踏む**。`./scripts/smoke-test.sh | tail -60` と繋ぐと終了コードが tail のものになり、
   失敗2件でも `exit 0` に見える(2026-08-21に実際に踏んだ)。ログはリダイレクトして後から読む
10. **煙試験の判定は「アプリのUIへ反映される時間」を待つ**。JSがページ内にバッジを出してから
   下部バーの件数へ反映されるまで数秒かかる(実測: バッジ5秒 → 下部バー10秒)。検出直後に1回だけ
   見る作りになっていて、**アプリは正常なのにテストだけが落ちていた**(2026-08-21修正)。
   落ちたらまずテスト側を疑う。同じ理由でバッジ検出のリトライも45秒→75秒へ伸ばした
